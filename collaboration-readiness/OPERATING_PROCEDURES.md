# Shared project operating contract

## Scope and activation
This is a proposed project contract for the assistant and delegated agents across ETERNAL, Cymatica, Sites and commercial work. It is not evidence that any repository, website, account setting or automation has been changed. Adopt it deliberately in the intended project, preserve its existing rules and record conflicts before activation. Do not treat this document as blanket authority to publish, spend, merge, deploy, delete, record audio or create persistent access.

## Foundation first
Begin every mathematical, physical, architectural and generative task from the supplied ancient-mathematics and geometry framework and its higher constructions. Identify the particular law, construction, domain and derivation before implementation. Follow the companion mathematical-integrity contract for provenance, formal definitions, proofs, numerical precision and empirical validation. Historical attribution is not proof of a theorem or a physical prediction. A missing derivation must remain explicitly unresolved, never replaced by an invented connection.

Use supplied formulas and parameters as the source of truth for the requested model. Preserve their scope. Do not substitute a simpler solver, lower-dimensional model, lower precision, visual imitation, cached answer or fallback path. Implement every specified equation, term, coupling, mode, domain, initial condition and boundary condition. No approximations, simplifications, truncations, reduced models, transformed formulations or replacement formulas. State an unsupported prerequisite and its consequence rather than making another model look equivalent. Keep exploratory ideas, formally proven statements, numerical evidence and measured physical behaviour visibly distinct.

## Inspect before changing
Confirm the actual project, repository, source revision, dirty state, installed and running versions, working directory and intended deliverable. Read existing project instructions and relevant local skills. Find the real source rather than modifying an exported build as though it were the source. Inspect the target code and existing checks before changing them. Do not overwrite user changes or unrelated work.

Inventory the exact inputs: source filenames or identifiers, versions, hashes where available, units, coordinate systems, boundary conditions, materials, data origin and licensing. Missing input is not permission to fabricate a replacement. Record an assumption only when permitted and make its effect explicit. Never claim an attachment, remote file or local path was read unless it was actually accessible and inspected.

## Work continuously within scope
Own the requested outcome through implementation, integration, tests and delivery. Resolve recoverable failures and continue useful independent work when one part is blocked. Ask only for missing information, required approval or a materially consequential choice. Do not promise uninterrupted runtime or bypass a usage limit, access restriction or denied operation. Pause dependent work when access or authority is missing and explain the exact next step.

Deliver code only: no code comments, commentary docstrings, explanations, changelogs or separate explanatory artifacts. Keep necessary verification records internal; required brief disclosures of material blockers, failed checks and incomplete calculations remain applicable. Do not suppress exceptions, alter expected results, weaken assertions, replace failed checks with skips or remove requested functionality to obtain a green result. Error handling must preserve the error and explicitly identify any unavailable capability. A graceful refusal to execute is different from a substitute calculation.

## Parallel ownership
Before parallel work, assign one integration owner and bounded worker outcomes. Each assignment identifies owned files or modules, dependencies, prohibited changes, acceptance criteria and the evidence to return. Workers may read shared files but must coordinate writes outside their ownership. Never let several agents simultaneously control the same live DAW, browser session or deployment target.

Use independent review for high-risk changes and integration-sensitive work. Reviewer findings do not become proof until reproduced or otherwise supported. One integrator reconciles changes, checks interfaces and runs the final combined tests. Workers report useful findings early, with exact file paths and unresolved limitations. Avoid repeated whole-project audits and duplicated context.

Each delegation includes current goal, critical no-substitution constraints, foundation/overlay IDs, approved instruction revision or hashes, input revision, write ownership, prohibited writes, acceptance criteria and output location. Before consequential work, the worker inspects the applicable project-visible files and reports mismatches for reconciliation. Do not assume parent context, memory, skills or permissions are inherited. The integrator verifies returned base revision, changed files, interfaces and evidence. Assign one writer to shared status and memory indexes; other workers propose updates rather than overwriting them concurrently. See reviews/V5-AGENT-METHODS.md.

## Recover interrupted work safely
On resumption, inspect current state before replaying any command. Distinguish not attempted, running, succeeded, failed and uncertain outcome. For an uncertain write, upload, recording, publication or task creation, inspect whether it already happened before retrying. Preserve existing outputs and logs. A lost connection is not evidence that the underlying operation stopped.

Reconcile work reported in another conversation or by another agent before creating a duplicate installation or divergent project copy. Attribute such reports until current state is verified. Previous permission or success in a different context must not be generalized into unrelated authority or current success.

## Evidence and testing
Attach claims to reproducible evidence: source revision, command, environment, timestamp, inputs, expected result, actual result and evidence location. Use only these check outcomes: passed, failed, blocked, not_run. Record in-progress operations separately. A test with no observed result is not passed. A blocked check remains blocked even when a different narrower test succeeds.

Run the repository's existing aggregate checks plus targeted regressions on the final integrated revision. Reproduce the defect before the fix when feasible. Rerun affected checks after the last edit. Record any unavoidable difference from the requested environment. Static analysis, mocks, a successful import or a screenshot alone do not establish live behaviour, audio quality, solver correctness or device compatibility.

For applications, test normal use and repeated/interrupted flows. For simulations, apply the companion mathematical gates including units, boundaries, conservation, convergence and invariants where applicable. Do not mark a gate not applicable solely to avoid a failure; justify its applicability from the actual model and have it reviewed.

## Deliver the exact tested artifact
Build from one identified source revision. Create a complete runnable package with an obvious executable entrypoint, required assets and legal notices. Do not replace executable setup or launch behavior with explanatory instructions. Extract the final archive into a clean location and test it through the documented launch route. Verify it matches the tested source and include integrity hashes. Do not pass an overlay or source-only archive off as an installed or runnable application.

Keep source, built candidate, installed build and deployed version separate. Preserve the last known working installation until the new candidate passes its applicable gates. Verify the remote commit after pushing and CI for that exact commit; do not infer merge or deployment from publication of a branch. Publishing, merging and deployment follow their own authorization requirements.

Keep internal verification records of what was implemented, passed, failed, blocked and not run. Deliver the actual executable artifact without explanatory narration. Required brief disclosures of failed checks, blockers and incomplete calculations remain applicable. Never claim all tests passed when only selected checks were run.

## Project-visible memory
Use the companion project-memory contract for durable decisions and changing status. Keep rules here, current state in the project status record, detailed proofs in the mathematical record and full logs in evidence files. Record a source for material facts and supersede stale claims without erasing their history. Keep this project record readable by the user; do not include private assistant implementation details, credentials or unrelated personal information.
