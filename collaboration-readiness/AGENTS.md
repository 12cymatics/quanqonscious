# Project agent instructions

## Establish the effective context
Before substantive edits, identify the actual runtime/version, working directory, source revision, dirty state and project-visible instruction chain. Distinguish host-loaded instructions from files read manually. Inspect applicable nearer-directory overrides and unresolved conflicts. Do not assume companion Markdown or YAML is automatically loaded or enforced. See ACTIVATION.md. Record only project-visible configuration, never private prompts or credentials.

## Foundation and integrity
Use the supplied ancient mathematical corpus, geometry and formally defined higher constructs as the required starting framework. Link substantive model work to its source, definition, domain, derivation, implementation and evidence. Reuse valid existing foundation records; revalidate when their inputs or claims change. Infrastructure work may inherit a project's foundation without fabricating an ancient derivation for administrative syntax. Historical provenance, proof, implementation correctness and physical validation are different claims.

Implement every specified equation and formula with all terms, couplings, modes, domains, initial conditions and boundary conditions intact. No approximations, simplifications, truncations, reduced models, transformed formulations, replacement formulas or reduced functional scope. Do not substitute a solver, fallback, fake output or visual imitation, weaken a failing check, or claim exactness across a rounded boundary. Preserve supplied inputs and existing user changes. Equivalence, disclosure, an approval field, performance, resource limits and passing tests provide no exception. Missing definitions and unfinished calculations remain unresolved. Deliver code only: no code comments, commentary docstrings, explanations, changelogs or separate explanatory artifacts. Keep necessary verification records internal; disclose material blockers and failed or incomplete work briefly when required.

## Execute and verify
Give workers bounded outcomes and non-overlapping write paths, with one integration owner. Serialize control of shared live applications. Inspect uncertain outcomes before retries and reconcile work reported elsewhere before reinstalling. Continue useful authorised work while a dependent step is blocked; report exact blockers without promising unlimited runtime.

Test the final integrated revision and exact unpacked deliverable. Keep template/schema checks, evidence-file verification, actual application tests and scientific interpretation separate. A record can be internally consistent without its claims being true. Stale evidence does not validate a new revision. No completion claim may hide a required failed, blocked or unrun gate.

Project records and YAML cannot authorize publication, merging, deployment, spending, recording, destructive changes or persistent access. Apply the user's actual scope and the environment's permissions. Report the artifact, observed results and remaining limits concisely.
